# Prácticas: Confidencialidad, Integridad, Disponibilidad y Trazabilidad

## 1. "Este archivo no es para ti"

### Objetivo

Descubrir mediante permisos reales:

- Confidencialidad
- Autenticación
- Autorización

### Crear un archivo

```bash
mkdir seguridad
cd seguridad

echo "INFORMACIÓN CONFIDENCIAL" > secreto.txt

ls -l secreto.txt
```

### Cambiar permisos

```bash
chmod 600 secreto.txt
ls -l secreto.txt
```

Pregunta:

> ¿Quién puede leer este archivo?

Después:

```bash
chmod 644 secreto.txt
ls -l secreto.txt
```

Pregunta:

> ¿Qué ha cambiado?

### Conceptos

- **Autenticación** → quién eres.
- **Autorización** → qué puedes hacer.
- **Confidencialidad** → quién puede acceder a la información.

### Variante

Crear dos usuarios:

```bash
sudo adduser alumno1
sudo adduser alumno2
```

Crear un archivo:

```bash
echo "Sueldo: 35000 €" > nominas.txt
```

Comprobar qué ocurre cuando `alumno2` intenta leerlo.

# 2. "El archivo sigue ahí, pero alguien lo ha cambiado"

### Objetivo

Comprender la **integridad** mediante hashes.

Crear:

```bash
echo "Transferir 100 €" > orden.txt
```

Calcular el hash:

```bash
sha256sum orden.txt
```

Ejemplo:

```text
a8f3... orden.txt
```

Modificar:

```bash
echo "Transferir 10000 €" > orden.txt
```

Volver a calcular:

```bash
sha256sum orden.txt
```

### Preguntas

> ¿El archivo sigue existiendo?

Sí.

> ¿Podemos acceder a él?

Sí.

> ¿Entonces está todo bien?

No.

El hash ha cambiado.

### Concepto

> **La integridad responde a una pregunta diferente: ¿la información sigue siendo la que debería ser?**

```text
ANTES
orden.txt
SHA-256 → XXXXX

        ↓ modificación

DESPUÉS
orden.txt
SHA-256 → YYYYY
```

# 3. "El servidor está encendido, pero no funciona"

### Objetivo

Comprender la **disponibilidad**.

Iniciar un servidor sencillo:

```bash
python3 -m http.server 8000
```

Acceder desde el navegador:

```text
http://localhost:8000
```

El servidor funciona.

Pararlo:

```text
CTRL + C
```

### Preguntas

> ¿El archivo ha desaparecido?

No.

> ¿Se ha modificado?

No.

> ¿Podemos acceder al servicio?

No.

### Conceptos

```text
CONFIDENCIALIDAD
¿Quién puede verlo?

INTEGRIDAD
¿Ha sido modificado?

DISPONIBILIDAD
¿Está accesible?
```

# 4. "¿Quién eres y qué puedes hacer?"

### Objetivo

Diferenciar **autenticación** y **autorización**.

Crear una estructura:

```text
empresa/
├── publico/
├── empleados/
└── direccion/
```

Simulación:

```text
Alumno  → empleado
Profesor → dirección
```

Situación:

> Juan consigue entrar en el sistema con su contraseña.

Pregunta:

> ¿Está autorizado para leer `direccion/salarios.txt`?

### Autenticación

```text
¿Quién eres?
     ↓
    Juan
```

### Autorización

```text
¿Qué puedes hacer?
     ↓
Leer empleados/
NO leer direccion/
```

### Idea clave

```text
AUTENTICACIÓN
    ↓
¿Quién eres?

AUTORIZACIÓN
    ↓
¿Qué puedes hacer?
```

# 5. "¿Quién ha hecho esto?"

### Objetivo

Introducir la **trazabilidad**.

Comprobar el usuario:

```bash
whoami
```

Información del usuario:

```bash
id
```

Usuarios que han iniciado sesión:

```bash
last
```

Historial:

```bash
history
```

Registros del sistema:

```bash
journalctl
```

### Pregunta

> Si cinco administradores utilizan un servidor, ¿cómo sabemos quién hizo algo?

### Trazabilidad

```text
Usuario
   ↓
Acción
   ↓
Fecha/hora
   ↓
Registro
```

Ejemplo:

```text
10:31 - juan  - inició sesión
10:35 - juan  - modificó usuarios
10:42 - ana   - modificó permisos
10:47 - pedro - reinició servicio
```

Pregunta:

> ¿Para qué sirve registrar estas acciones?

# 6. Juego: ¿C, I o D?

## Caso 1

> Un alumno consigue acceder a las notas de todos sus compañeros.

**C — Confidencialidad**

---

## Caso 2

> Un atacante cambia un 5 por un 9.

**I — Integridad**

---

## Caso 3

> Un ransomware cifra los archivos y los usuarios no pueden acceder a ellos.

**D — Disponibilidad**

También puede afectar a **Integridad**.

---

## Caso 4

> Se rompe el disco donde está la base de datos.

**D — Disponibilidad**

---

## Caso 5

> Un administrador modifica una configuración y no queda ningún registro.

**Trazabilidad**

---

## Caso 6

> Un usuario introduce correctamente su contraseña, pero no puede acceder a `/direccion`.

```text
Autenticación → correcta

Autorización → no permitida
```

---

## Caso 7

> Un atacante modifica una página web.

**I — Integridad**

---

## Caso 8

> Un servidor recibe tantas peticiones que deja de responder.

**D — Disponibilidad**

# 7. Reto final

## Escenario

> Una empresa tiene un servidor con una base de datos de clientes. Un atacante consigue la contraseña de un administrador. Entra en el servidor, copia la base de datos, modifica varios registros y finalmente detiene el servidor.

### Encontrad todos los problemas de seguridad

```text
1. Consigue la contraseña
       ↓
2. Accede a información
       ↓
3. Copia la base de datos
       ↓
4. Modifica registros
       ↓
5. Detiene el servidor
```

### Clasificación

| Acción | Principio |
|---|---|
| Accede a datos que no debería | **Confidencialidad** |
| Copia la base de datos | **Confidencialidad** |
| Modifica registros | **Integridad** |
| Detiene el servidor | **Disponibilidad** |
| Utiliza una cuenta de administrador | **Autenticación / autorización** |
| Saber qué usuario lo hizo | **Trazabilidad** |

---

# 8. Idea final

> **La seguridad no consiste únicamente en impedir que entren. También consiste en controlar qué pueden hacer, detectar qué han hecho y garantizar que los datos y servicios siguen siendo correctos y accesibles.**

```text
CONFIDENCIALIDAD
¿Quién puede acceder?

INTEGRIDAD
¿La información es correcta?

DISPONIBILIDAD
¿El servicio está accesible?

AUTENTICACIÓN
¿Quién eres?

AUTORIZACIÓN
¿Qué puedes hacer?

TRAZABILIDAD
¿Qué has hecho y cuándo?
```
